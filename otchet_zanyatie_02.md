### 1. Проектирование структуры папок проекта (Вариант 5)

Для разработки REST API-сервиса спроектирована масштабируемая модульная структура, отвечающая принципам *Clean Architecture*, стандартам *12-Factor App* и требованиям безопасной разработки.

Все имена каталогов и файлов составлены в строгом соответствии с правилами:
- исключительно символы латинского алфавита;
- нижний регистр символов (*lowercase*);
- отсутствие пробелов и спецсимволов;
- разделение слов через дефис (*kebab-case*) для инфраструктурных файлов или подчёркивание (*snake_case*) для модулей Python.

#### Назначение элементов структуры:

1. **`app/`** — корневой пакет исходного кода бэкенд-сервиса:
   - **`main.py`** — точка входа в ASGI-приложение (инициализация FastAPI/uvicorn, подключение роутеров, middleware CORS и обработчиков ошибок).
   - **`api/v1/`** — конечные точки (эндпоинты) REST API с версионированием URL (`/api/v1/auth`, `/api/v1/users`).
   - **`core/`** — общесистемные модули: глобальная конфигурация (`config.py`), чтение переменных окружения, утилиты шифрования паролей и генерации JWT-токенов (`security.py`).
   - **`models/`** — декларативные модели таблиц реляционной БД (SQLAlchemy ORM).
   - **`schemas/`** — схемы валидации и сериализации входных/выходных DTO (Pydantic).
   - **`services/`** — слой бизнес-логики, изолирующий обработку запросов от прямого обращения к БД.
2. **`migrations/`** — система версионирования схемы базы данных (Alembic):
   - **`alembic.ini`** и **`env.py`** — скрипты конфигурации подключения к СУБД.
   - **`versions/001_initial_tables.py`** — атомарный файл миграции для воспроизводимого создания таблиц.
3. **`tests/`** — среда автоматизированного тестирования (pytest):
   - **`conftest.py`** — изолированные фикстуры тестовой сессии и подмена базы данных на in-memory экземпляр.
   - **`test_api.py`**, **`test_auth.py`** — модульные и интеграционные тесты эндпоинтов.
4. **`docs/`** — документация проекта:
   - **`openapi.json`** — машиночитаемая спецификация интерфейсов Swagger / OpenAPI.
   - **`api.md`** — руководство разработчика по интеграции с внешними клиентами.
5. **`data/`** — директория статических наборов данных и фикстур (`initial_data.csv`) для первоначального наполнения БД (*database seeding*).
6. **Конфигурационные и инфраструктурные файлы:**
   - **`.env.example`** — публичный шаблон переменных окружения без реальных секретов.
   - **`.gitignore`** — правила исключения конфиденциальных файлов (`.env`), виртуальных окружений (`.venv/`) и кэша (`__pycache__/`) из репозитория Git.
   - **`Dockerfile`** и **`docker-compose.yml`** — декларативные сценарии контейнеризации сервиса и СУБД PostgreSQL.
   - **`pyproject.toml`** — манифест зависимостей и настроек сборщика пакетов.
   - **`README.md`** — главная инструкция по установке, конфигурированию и запуску сервиса.

### 2. Обоснование выбора операционных систем

- **ОС для разработки (Workstation):**  
  Выбрана ОС **Windows 11 с подсистемой WSL2 (Ubuntu 24.04 LTS)**. Данная связка обеспечивает комфортную работу с графическими средами разработки (VS Code, JetBrains), браузерами и коммуникаторами, одновременно предоставляя разработчику полноценное ядро Linux с идентичной POSIX-совместимой файловой системой и терминалом, что исключает расхождения при локальной отладке кода.

- **ОС для сервера (Production):**  
  Выбрана ОС **Linux (дистрибутив Ubuntu Server 24.04 LTS или легковесный Alpine Linux в Docker-контейнере)**. Данный выбор обусловлен высокой энергоэффективностью и производительностью за счет отсутствия графического интерфейса (GUI), строгой моделью разграничения прав доступа (DAC/MAC), стабильностью ядра без необходимости частых перезагрузок и нативной поддержкой контейнеризации.

### 3. Анализ путей внутри проекта

В структуре проекта определены следующие пути к файлам:

1. **Абсолютный путь:**  
   ```text
   /home/developer/projects/rest-api-service/app/main.py
   ```
   *Характеристика:* Полный путь от корневого каталога файловой системы (`/`). Он однозначно определяет положение файла в дереве ОС независимо от текущей рабочей директории.  
   *Важное правило разработки:* Использование абсолютных путей внутри исходного кода недопустимо, так как путь жестко привязан к конкретному пользователю (`developer`) и файловой системе одной машины, что приведет к фатальному сбою (`FileNotFoundError`) при запуске на сервере или машине коллеги.

2. **Относительный путь № 1 (от корня проекта):**  
   ```text
   ./migrations/versions/001_initial_tables.py
   ```
   *Характеристика:* Путь отсчитывается от текущего каталога (`./`), в котором запускается команда миграций (например, `alembic upgrade head`). Он переносим и будет корректно работать в любой среде, где развернут репозиторий.

3. **Относительный путь № 2 (с выходом на родительский уровень):**  
   ```text
   ../app/core/config.py
   ```
   *Характеристика:* Путь указан относительно директории `tests/`. Использование маркера `../` обозначает переход на один уровень вверх в родительский каталог `rest-api-service/` с последующим переходом в пакет приложения к файлу конфигурации ядра. Это обеспечивает корректный локальный импорт параметров в тестах без привязки к глобальным абсолютным путям.

### 5. Продвинутая часть: Единое окружение команды

#### 5.1. Архитектура решения
Для гарантированного устранения различий в окружении в команде настраивается стандартизированный стек:
1. **Контейнеризация на базе Docker:** Сервис и внешние зависимости (СУБД PostgreSQL, брокер Redis) упаковываются в контейнеры при помощи файлов `Dockerfile` и `docker-compose.yml`.
2. **Подсистема WSL2 для разработчиков на Windows:** Разработка ведется внутри среды Linux (Ubuntu), что гарантирует работу в нативной файловой системе ext4 и совпадение формата окончаний строк.
3. **Строгая фиксация версий зависимостей:** Использование lock-файлов (`poetry.lock` или `requirements.txt` с фиксированными хэшами и версиями библиотек), а также базового Docker-образа с четко указанной версией (`python:3.12-slim-bookworm`).

#### 5.2. Почему это навсегда устраняет баг «работает только у меня»
Баг «works on my machine» возникает из-за невидимой разницы в фундаментальных слоях компьютерной системы:

1. **Различие в чувствительности файловых систем к регистру:**
   - На файловой системе Windows (NTFS) регистр не различается: вызов `open("data/Users.csv")` успешно откроет файл `data/users.csv`.
   - На сервере под управлением Linux (ext4) регистр строго учитывается: этот же код выбросит исключение `FileNotFoundError`, обрушив приложение.
2. **Разделители путей и символы перевода строк (CRLF vs LF):**
   - Windows сохраняет строки с окончанием `\r\n` (CRLF), а Linux — `\n` (LF). Скрипт инициализации с CRLF на Linux завершится ошибкой `/bin/bash^M: bad interpreter`.
   - Контейнер изолирует сборку и принудительно исполняет код по стандартам POSIX.
3. **Разночтение версий системных библиотек:**
   - Локально у разработчика может быть установлен Python 3.12, а на тестовом сервере — 3.10. Использование нового синтаксиса (например, сопоставление с образцом `match/case` или новые операторы типов) приведет к `SyntaxError`.
   - В Docker-контейнер упаковывается конкретный бинарный интерпретатор и точные версии C-библиотек (`libpq-dev` для PostgreSQL), одинаковые для всех членов команды.
4. **Изоляция и воспроизводимость:**
   - Контейнер представляет собой стандартизированный программный «сэндбокс», не зависящий от того, какая ОС установлена на хост-компьютере разработчика. Команда `docker compose up --build` на Windows, macOS или Linux создает идентичное окружение с точностью до бита.
